# احراز هویت و مدیریت نشست

## طراحی پیاده‌سازی

رمز با Argon2 در ابزار `create_user.py` هش می‌شود. ورود از JSON انجام می‌شود؛ این API یک سامانهٔ ورود ساده است و پیاده‌سازی کامل پروتکل OAuth/OIDC محسوب نمی‌شود. پیام رمز اشتباه و کاربر ناموجود یکسان است؛ مسیر کاربر ناموجود نیز بررسی هش ساختگی انجام می‌دهد.

JWT با PyJWT و الگوریتم ثابت HS256 امضا می‌شود. سرور فقط همین الگوریتم را می‌پذیرد؛ الگوریتم دلخواه از هدر توکن انتخاب نمی‌شود. امضا، issuer، audience، زمان انقضا، nbf و claimهای اجباری بررسی می‌شوند. `sub` شناسهٔ کاربر، `sid` شناسهٔ نشست، `jti` شناسهٔ تصادفی توکن و `type` یکی از access، refresh یا csrf است. Refresh به‌جای Access پذیرفته نمی‌شود. JWT رمزگذاری نشده است؛ رمز یا اطلاعات حساس کاربر در payload آن قرار ندارد. [مستندات FastAPI](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)

Access Token حداکثر ۱۵ دقیقه و Refresh Token حداکثر ۷ روز اعتبار دارد. سقف هفت‌روزهٔ نشست از زمان ورود ثابت است؛ refresh آن را بی‌نهایت تمدید نمی‌کند. هر refresh توکن جدید با jti جدید می‌سازد. تنها هش SHA-256 توکن refresh در دیتابیس ذخیره می‌شود؛ چون توکن تصادفی و امضاشده است، این هش با هش رمز انسانی کاربرد متفاوتی دارد.

به‌جای پاک‌کردن رکورد نشست، logout آن را revoked می‌کند. هر درخواست محافظت‌شده علاوه بر JWT وضعیت نشست را از دیتابیس بررسی می‌کند؛ بنابراین کپی Access Token هم پس از logout رد می‌شود. این طراحی عمداً کاملاً stateless نیست و برای ابطال فوری به یک خواندن دیتابیس نیاز دارد.

## چرخش Refresh و بازپخش

refresh با یک UPDATE شرطی فقط وقتی موفق می‌شود که هش ذخیره‌شده هنوز برابر توکن ارسالی باشد. دو درخواست هم‌زمان نمی‌توانند هر دو همان توکن را مصرف کنند. ارائهٔ توکن قدیمیِ معتبر از نظر امضا، نشست مربوط را باطل می‌کند. این کار سرقت و بازپخش را محدود می‌کند ولی ممکن است refresh هم‌زمان در دو تب یا تکرار درخواست پس از قطع شبکه نیز خروج اجباری ایجاد کند. کلاینت باید refresh را سری کند؛ نمونهٔ این پروژه ترتیبی است. برای چند تب هماهنگی مشترک لازم است. [راهنمای چرخش refresh در RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)

## کوکی‌ها

| کوکی | HttpOnly | Secure | SameSite | Path | کاربرد |
|---|---|---|---|---|---|
| __Host-access | بله | بله | Strict | / | احراز هویت درخواست |
| __Host-refresh | بله | بله | Strict | / | تمدید نشست |
| __Host-csrf | خیر | بله | Strict | / | انتقال CSRF به هدر |

هیچ Domain تعیین نمی‌شود. پیشوند `__Host-` با Secure و Path=/، کوکی را به همان میزبان محدود می‌کند. Path=/ برای refresh نیز لازم است تا پیشوند معتبر بماند؛ به‌همین دلیل refresh به مسیرهای دیگر همان میزبان هم ارسال می‌شود و فقط endpoint مناسب آن را مصرف می‌کند. Max-Age با عمر باقی‌مانده تنظیم می‌شود و حذف کوکی با همان نام و مسیر انجام می‌گیرد. پاسخ‌ها `Cache-Control: no-store` دارند.

## چرا کوکی؟ مقایسهٔ دقیق XSS و CSRF

کوکی HttpOnly باعث می‌شود جاوااسکریپت نتواند مقدار Access/Refresh را با document.cookie بخواند؛ این مزیت نسبت به نگه‌داری توکن در localStorage یا متغیر قابل‌دسترسی برای اسکریپت، سرقت مستقیم توکن را دشوارتر می‌کند. اما XSS همچنان می‌تواند از مرورگر قربانی درخواست معتبر بفرستد یا دادهٔ پاسخ را بخواند. HttpOnly جایگزین escape کردن خروجی، جلوگیری از اجرای محتوای نامطمئن و CSP مناسب نیست.

کوکی به‌خودی‌خود مزیت CSRF ندارد؛ مرورگر آن را خودکار ارسال می‌کند و همین می‌تواند خطر CSRF ایجاد کند. توکن Authorization که اسکریپت عمداً به هدر اضافه می‌کند معمولاً این رفتار خودکار را ندارد. انتخاب بین این دو به نوع کلاینت وابسته است؛ کوکی همیشه امن‌تر نیست. [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

در این پروژه برای همهٔ درخواست‌های تغییردهنده، شامل login/refresh/logout، سه لایه اعمال شده است: SameSite=Strict، تطبیق دقیق Origin با APP_ORIGIN و بررسی توکن CSRF امضاشده در کوکی و هدر X-CSRF-Token. بعد از ورود، هش CSRF به نشست هم متصل است تا توکن نشست دیگری قابل‌استفاده نباشد. توکن CSRF عمداً HttpOnly نیست و به‌تنهایی مجوز ورود نیست. نبود Origin یا توکن نامعتبر با 403 رد می‌شود. CORS باز فعال نشده و طراحی برای کلاینت هم‌مبدأ است. [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)

## چرخهٔ کلاینت

۱. GET /auth/csrf را با cookie jar فراخوانی کند.
۲. POST /auth/login را با نام کاربری، رمز، کوکی CSRF، Origin و هدر X-CSRF-Token بفرستد.
۳. پس از ورود، CSRF جدید را دریافت کند؛ Access/Refresh در JSON برگردانده نمی‌شوند.
۴. هزینه‌ها را با کوکی‌ها بخواند؛ برای ایجاد/ویرایش/حذف هدر CSRF نیز لازم است.
۵. اگر Access منقضی شد یا مرورگر کوکی منقضی را حذف کرد، POST /auth/refresh را یک بار انجام دهد و درخواست اولیه را یک بار تکرار کند.
۶. اگر refresh شکست خورد یا سقف هفت‌روزه تمام شد، ورود مجدد لازم است؛ حلقهٔ تکرار نامحدود نباید ایجاد شود.
۷. برای خروج POST /auth/logout را با CSRF بفرستد. خروج حتی با Access منقضی و Refresh معتبر کار می‌کند.

در مرورگر از `credentials: "same-origin"` استفاده می‌شود و Origin را خود مرورگر تعیین می‌کند. نمونهٔ Python در examples/session_client.py همین چرخه را پیاده‌سازی و تست می‌کند. خواندن توکن CSRF توسط اسکریپت مجاز است؛ خواندن کوکی‌های احراز هویت مجاز نیست.

## خطاها

| وضعیت | detail | واکنش |
|---|---|---|
| 401 | invalid_credentials | نام کاربری/رمز صحیح لازم است |
| 401 | authentication_required | Access موجود نیست؛ یک تلاش refresh، سپس ورود |
| 401 | token_expired | Access: refresh؛ Refresh: ورود مجدد |
| 401 | invalid_token | توکن دستکاری‌شده، نوع/claim/امضا نامعتبر؛ ورود مجدد |
| 401 | session_invalid | نشست باطل یا منقضی؛ ورود مجدد |
| 401 | refresh_reused | بازپخش؛ نشست باطل و کوکی‌ها پاک می‌شوند |
| 403 | csrf_failed | درخواست اجرا نمی‌شود؛ Origin و CSRF بررسی شوند |
| 404 | Expense not found | هزینه ناموجود یا متعلق به کاربر دیگر |
| 422 | خطاهای Pydantic | اصلاح ساختار ورودی |

خطاهای refresh با 401 کوکی‌ها را پاک می‌کنند. انقضای Access کوکی Refresh را پاک نمی‌کند. اگر خود CSRF هم منقضی باشد، بررسی اولیه 403 می‌دهد؛ GET /auth/csrf و ورود مجدد چرخه را از نو آغاز می‌کند. CSRF متفاوت با نشست باعث 403 می‌شود و اجازهٔ ابطال نشست را نمی‌دهد.

## مالکیت و migration

هزینهٔ جدید owner_id را از کاربر احرازشده می‌گیرد، نه از بدنهٔ درخواست. فهرست، خواندن، ویرایش و حذف همگی به owner_id محدودند. برای جلوگیری از افشای وجود رکورد، هزینهٔ دیگری نیز 404 است. در migration 0002 هزینه‌های قدیمی owner_id=NULL می‌مانند و برای هیچ کاربری قابل مشاهده نیستند. انتساب دادهٔ قدیمی بدون شواهد مالکیت انجام نشده است.

## محدودیت‌های آموزشی

این پروژه rate limiting ورود، MFA، بازیابی/تغییر رمز، مدیریت دستگاه‌ها و پاک‌سازی دوره‌ای نشست‌های قدیمی ندارد. پیش از سرویس عمومی باید این موارد، HSTS روی HTTPS واقعی، مدیریت و چرخش کلید، جلوگیری از ثبت رمز/توکن در log و سیاست دسترسی عملیاتی تکمیل شوند. مقدار test-only-long-password فقط در تست موقت استفاده می‌شود و حساب پیش‌فرض برنامه نیست. هیچ استقرار عمومی یا ممیزی امنیتی مستقل ادعا نشده است.
