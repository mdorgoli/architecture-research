# پشتیبانی فارسی و انگلیسی

## انتخاب زبان

اولویت انتخاب: پارامتر `lang`، سپس هدر `Accept-Language`، سپس انگلیسی (`en`). نمونه‌ها:

```http
GET /welcome?lang=fa
Accept-Language: en
```

```json
{"language":"fa","message":"به سامانهٔ مدیریت هزینه‌ها خوش آمدید."}
```

```http
GET /about
Accept-Language: en;q=0.3, fa-IR;q=0.9
```

پاسخ دوم فارسی است. وزن بزرگ‌تر اولویت دارد؛ در وزن برابر ترتیب هدر تعیین‌کننده است. `fa-IR` به `fa` و `en-US` به `en` تبدیل می‌شود. مقدار q=0 از نامزدهای انتخاب کنار می‌رود و wildcard پشتیبانی می‌شود. ورودی دارای وزن نامعتبر نادیده گرفته می‌شود. پارامتر نامعتبر یا زبان پشتیبانی‌نشدهٔ Query مستقیماً به انگلیسی برمی‌گردد و هدر را بررسی نمی‌کند.

این مذاکرهٔ ساده فقط زبان پایه را پشتیبانی می‌کند، نه تفاوت لهجه‌ها یا تمام قواعد BCP 47. اگر هیچ انتخابی باقی نماند، حتی اگر همه q=0 باشند، سیاست این API پاسخ انگلیسی است و 406 برنمی‌گرداند. طول پردازش هدر محدود است. مسیر فایل ترجمه فقط از فهرست زبان‌های مجاز ساخته می‌شود؛ مقدار ورودی کاربر مسیر فایل نیست.

## فایل‌ها و Dependency Injection

```text
i18n.py
locales/
  en/LC_MESSAGES/messages.po
  en/LC_MESSAGES/messages.mo
  fa/LC_MESSAGES/messages.po
  fa/LC_MESSAGES/messages.mo
scripts/compile_translations.py
requirements-i18n.txt
test_i18n.py
```

PO متن قابل ویرایش مترجم و MO نسخهٔ کامپایل‌شده برای اجرای برنامه است. `gettext.GNUTranslations` فایل MO را بارگذاری می‌کند؛ مسیر بر اساس مکان i18n.py ساخته می‌شود و به پوشهٔ اجرای دستور وابسته نیست. catalog در cache نگه‌داری می‌شود، ولی انتخاب زبان برای هر درخواست جداست. از `gettext.install`، متغیر سراسری زبان جاری یا تغییر locale فرایند استفاده نشده تا درخواست‌های هم‌زمان زبان یکدیگر را تغییر ندهند. [مستندات gettext](https://docs.python.org/3/library/gettext.html)

نمونهٔ وابستگی در endpoint:

```python
Language = Annotated[Translator, Depends(get_translator)]

@app.get("/welcome")
def welcome(translator: Language):
    return {
        "language": translator.language,
        "message": translator.gettext("Welcome to the expense manager."),
    }
```

مدیریت خطاها بیرون از DI endpoint اجرا می‌شود و همان تابع `get_translator(request)` را فراخوانی می‌کند تا سیاست انتخاب زبان یکسان بماند. [راهنمای مدیریت خطای FastAPI](https://fastapi.tiangolo.com/tutorial/handling-errors/)

## بخش‌های ترجمه‌شده

- GET `/welcome` و `/about`: نمونه‌های عمومی.
- GET `/expenses/summary`: فقط برای کاربر واردشده، تعداد هزینه‌های همان کاربر با ngettext.
- POST `/auth/login` و `/auth/refresh`: پیام موفقیت.
- خطاهای احراز هویت، CSRF، هزینهٔ ناموجود، مسیر ناموجود و متد نامعتبر.
- خطاهای ورودی Pydantic و JSON: پیام عمومی و متن هر خطا. نوع خطای ناشناخته پیام ترجمه‌شدهٔ عمومی می‌گیرد.

پاسخ‌ها هدر `Content-Language` و `Vary: Accept-Language` دارند. سیاست `Cache-Control: no-store` نسخهٔ احراز هویت حفظ شده است. Query نیز بخشی از URL است؛ اگر بعداً cache اضافه شود باید زبان در کلید cache لحاظ شود.

نام فیلدهای JSON، شناسه‌ها، نام کاربری، توضیح واردشده توسط کاربر، توکن‌ها و عدد مبلغ ترجمه نمی‌شوند. تاریخ، واحد پول، ارقام فارسی، UI راست‌به‌چپ و مستندات Swagger به این مرحله اضافه نشده‌اند. پاسخ‌های 204 همچنان بدون بدنه‌اند. خطای داخلی غیرمنتظره 500 از این نگاشت عبور نمی‌کند و جزئیات داخلی آن به کاربر داده نمی‌شود.

## قرارداد پایدار برای کلاینت

کدهای `detail` خطاهای احراز هویت و HTTP ثابت می‌مانند و `message` برای نمایش به کاربر ترجمه می‌شود. نمونه:

```json
{"detail":"authentication_required","message":"برای ادامه وارد حساب خود شوید."}
```

نمونهٔ خلاصه:

```json
{"count":2,"message":"شما 2 هزینه دارید.","language":"fa"}
```

در موفقیت ورود/refresh، `message` اکنون متن نمایشی است و کد قبلی در فیلد `code` قرار دارد. کلاینت باید تصمیم تمدید نشست را بر اساس HTTP status و `detail` بگیرد، نه متن ترجمه. نمونه‌کلاینت قبلی به همین دلیل همچنان کار می‌کند.

خطاهای اعتبارسنجی `detail` را به‌شکل فهرست با `type`، `loc` و `msg` حفظ می‌کنند؛ `input` و `ctx` در پاسخ بازتاب نمی‌شوند تا رمز یا بدنهٔ حساس در خطا تکرار نشود. کنترل‌های احراز هویت و مالکیت تغییر نکرده‌اند.

## ترجمه و افزودن زبان

نمونهٔ PO فارسی:

```po
msgid "Welcome to the expense manager."
msgstr "به سامانهٔ مدیریت هزینه‌ها خوش آمدید."
```

۱. پوشهٔ `locales/en/LC_MESSAGES` را برای زبان جدید، مثلاً `de`، کپی کنید و messages.po را ترجمه کنید.
۲. metadata شامل `Language`، UTF-8 و `Plural-Forms` را مطابق زبان جدید تنظیم کنید؛ قاعدهٔ جمع انگلیسی را برای همهٔ زبان‌ها کپی نکنید.
۳. کد زبان را به `SUPPORTED_LANGUAGES` در i18n.py اضافه کنید. زبان پیش‌فرض در `DEFAULT_LANGUAGE` است.
۴. ابزار ترجمه را نصب و فایل‌ها را کامپایل کنید:

```powershell
.venv\Scripts\python -m pip install -r requirements-i18n.txt
.venv\Scripts\python scripts/compile_translations.py
```

۵. هم PO و هم MO را در Git ثبت کنید. سرور را دوباره راه‌اندازی کنید تا cache قدیمی کنار گذاشته شود.
۶. تست پیام نمونه، مذاکرهٔ زبان، قواعد جمع و خطاها را اضافه و `python -m unittest -v` را اجرا کنید.

MOهای دو زبان فعلی در مخزن موجودند؛ اجرای API به polib نیاز ندارد و فقط هنگام ویرایش ترجمه به آن نیاز است. فایل MO گمشده یا خراب هنگام راه‌اندازی خطا می‌دهد تا ترجمهٔ ناقص بی‌صدا منتشر نشود. msgid ترجمه‌نشده به متن منبع انگلیسی برمی‌گردد.

برای افزودن پیام تازه، یک جملهٔ کامل با msgid ثابت به هر PO اضافه کنید و از `translator.gettext` در کد استفاده کنید. برای متن دارای تعداد از ngettext استفاده کنید. جای‌نگهدار نام‌دار مانند `%(count)d` باید در ترجمه بدون تغییر بماند؛ قطعات جمله را به‌هم نچسبانید، چون ترتیب کلمات بین زبان‌ها متفاوت است. ابزار کامپایل ترجمهٔ خالی، fuzzy و نام جای‌نگهدار ناسازگار را رد می‌کند.

## نکات و چالش‌ها

کیفیت ترجمه به بازبینی انسانی نیاز دارد؛ ترجمهٔ لفظی برای پیام خطا همیشه روشن نیست. قالب‌بندی تاریخ و پول با ترجمهٔ جمله فرق دارد. ترتیب کلمات، قواعد جمع و راست‌به‌چپ باید در کلاینت هم در نظر گرفته شوند. فایل‌های ترجمه مانند کد باید از منبع قابل اعتماد باشند. کلیدهای ماشینی ثابت، تست هم‌زمانی و تست catalog مانع شکستن کلاینت هنگام تغییر متن می‌شوند.
